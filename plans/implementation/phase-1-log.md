Phase 1 established the foundation for context-optimized agent behavior by introducing a plugin-based indexer and injecting a compact project skeleton into the model's system prompt.

## Why It Was Done

### The Problem

Coding agents typically send entire source files to the model when reading code. For a 300-line file, that's ~3,000–5,000 tokens — even when the agent only needs to understand or edit a single function. Research shows:

- **Read operations consume 67–76% of total tokens** in typical agent sessions (SWE-Pruner)
- **Attention degrades** as context length increases — models perform worse with more tokens, even when retrieval is perfect
- **Small local models** (7B–14B) have limited effective context; bloated reads push them past their usable window

### The Approach

Instead of sending whole files blindly, we give the model a **project skeleton** up front — all function/class/interface signatures, no bodies — so it can orient itself and make better-targeted `read_file` calls. The skeleton is generated by parsing source code with language-specific plugins and is injected into the system prompt at session start.

### Why a Plugin Architecture

The optimization strategy (code maps, token budgeting) is language-agnostic. Only the parsing is language-specific. A plugin interface lets us:

- Use the **best parser per language** (e.g., TypeScript compiler API for TS, not a generic tree-sitter)
- Support **multiple languages** without hardcoding each one
- Enable **community contributions** — language experts can add plugins without touching the agent core

Phase 1 implements the interface and ships the TypeScript plugin as the reference implementation.

## Value to the Product

### 1. Better Orientation

The model receives a compact overview of the entire project (symbols, locations, signatures) before its first tool call. It can see that `parseResponse` lives in `src/model/client.ts` and that `CodingAgent.runTurn` calls `modelClient.chat` — without reading any full files.

### 2. Smarter read_file Decisions

With the code map, the model can choose which files to read based on structure, not guesswork. It knows where to look for a given symbol instead of searching blindly.

### 3. Fixed Token Cost for Orientation

The code map is ~500–1,500 tokens regardless of project size (thanks to token budgeting). That's a one-time cost at session start, compared to reading multiple large files to "explore" the codebase.

### 4. Foundation for Phase 2+

Phase 1 does not add new tools — the model still uses `read_file`. But it establishes:

- The `ProjectIndex` that Phase 2's `read_symbol` tool will query
- The plugin interface that Phase 3's dependency resolution will extend
- The graceful-degradation pattern (indexing fails → agent works as before)

### 5. Extensibility

The plugin loader is designed for future expansion: local plugins, user plugins, npm packages. Phase 1 only loads the built-in TypeScript plugin, but the architecture is ready for more.

---

## Summary

Phase 1 delivers **structural awareness** to the agent — a lightweight project skeleton in the system prompt — without changing how the model reads or edits files. It reduces wasted exploration, improves targeting of `read_file` calls, and sets up the infrastructure for the higher-impact Phase 2 (`read_symbol`) and Phase 3 (dependency graph) work.
